# CLAUDE.md — `app/` (native)

The Expo / React Native player for iOS and Android, with its own `package.json`, `node_modules` and `eas.json`. Read [`docs/TESTING.md`](docs/TESTING.md) before touching native config, a dependency or the RNTP patch: its architecture-critical section holds the reasoning behind the native rules below, and the files named in the other rules explain those.

- **New Architecture is mandatory**, and `patches/react-native-track-player+4.1.2.patch` is what makes RNTP run under it (Android crashes on the first playback event without it). Editing the patch or upgrading RNTP/KotlinAudio follows TESTING.md's adapter and device-check rules.
- **`ios/` and `android/` are generated** (Continuous Native Generation, gitignored). Change `app.json`, `plugins/` or `assets/`, never the native folders.
- **iOS uses the UIScene life cycle (`expo-build-properties` `ios.enableSceneSupport`).** Without it an iOS 27-SDK build is killed at launch on iOS 27; drop it with the SDK 58 upgrade, whose template does the same (TESTING.md).
- **OTA cannot reach native code.** The Live Activity card (Lock Screen, Dynamic Island, the Apple Watch Smart Stack) is SwiftUI under `targets/live-activity/` and `modules/live-activity/ios/`, so a change there ships only in a new binary, like a dependency, `patches/`, plugin or native `app.json` change; the JS that drives it (`src/hooks/useLiveActivity.ts`) is OTA-able. The same holds for the App Intents (Siri, Shortcuts): Swift under `targets/live-activity/_shared/` and `modules/app-intents/ios/`, JS under `src/intents/`. `SubwaveLiveAttributes.swift` is compiled into both and must stay byte-identical (`npm test` checks): a mismatch stops the card rendering instead of failing the build.
- **Android Auto's browse session is RNTP's own**, reached through the patch's `MediaBrowserBridge`; `modules/android-auto` only lists stations, and a pick reaches `service.ts` as `remote-play-id`. Play enforced against a TTS-reading app once (#477); TESTING.md has the history and the device check.
- **The CarPlay app is off unless `SUBWAVE_CARPLAY=1` is set at prebuild** (`plugins/withCarPlay.js`), because a device build can't be signed with the CarPlay entitlement until Apple grants it. Unset, the Info.plist and entitlements are unchanged. Its Swift is `targets/live-activity/_shared/SubwaveCarPlay.swift` (TESTING.md).
- **The station password is not the station login** (#478). Every check is the fail-closed `POST /station-auth`, and only the controller's own answers count: a 200 with its `{ ok: true }` body is a right password and a 401 with its `{ ok: false }` body a wrong one, while anything else keeps a saved password and saves no typed one (`stationAuthResult`, #2143, #2164); the password rides the stream as `?auth=` so Cast works; `createApi` reads it through a getter because the feed reset and the Live Activity lifecycle key on the `api` object's identity, so rebuilding the client on unlock would reset both. While playback is stuck, `src/lib/stuck-password-check.ts` asks again after every answer but a denial, never within 120 s of the last check or before a 429's `Retry-After` runs out, capped at the route's own window: it allows a household's address 20 attempts per 15 minutes (#2141, #2164). When the gate's stop takes a tuned-in listener off the air, the right typed password tunes them back in with no second press (`src/lib/gate-resume.ts`, the twin of the web's `lib/gateResume.ts`), through `tune`, so it is a listener's own load in `stream-recovery.ts`. `useStationGate` outlives a station switch, so the hold names the `api` it was taken on, and `tune` toggles, so it never runs for a listener already tuned in.
- **Every stream reload goes through `src/lib/stream-recovery.ts` while the player is mounted** (#2114, #2139): one at a time, and never on a state event alone. A listener's own load (a tune-in, a retune, a Play from the lock screen, a headset, CarPlay or Bluetooth) always loads, queued behind one in flight. `service.ts` hands a remote Play to the mounted player (`src/lib/remote-play.ts`) and loads directly only when none is mounted, which Android's headless service allows; an App Intent's tune-in and station switch do the same (`src/intents/tune-flow.ts`), and so does an Android Auto pick. The watchdog, churn guard and error backoff each check the native media clock first, because a reload re-sends Icecast's burst and the listener hears audio twice; a regained link reads it through the pending check it brings forward, and with none pending reloads at once. Every load is checked even when it reports no state (iOS drops a repeated Loading, #2143), and an automatic reload is a failure until its item stays up, so a hung station backs off to 60 s. Playing resets that only provisionally: an item that fails after stopping within 4 s of its first Playing, judged from the moment it stopped, takes the reset back, and the reload after it waits at most 16 s, so a stream cut a moment in can't reload 35-60 times a minute. A stall never counts, however early, and stays on the 6 s watchdog: Icecast closes a stalled socket about 15 s after its source stops, so a longer wait hears that close as a failure, and a flapping source climbs to a minute of silence. A hold counts as the item's Playing, because JS can miss the real one. None of this runs during an iOS audio interruption (a call, Siri), which freezes the clock without a state event.
- **The idle skip changes only the native rate, never seeks or reloads** (#9, the port of web's `idleSkip.ts`, kept in step with it). It runs on an MP3 load in the foreground, reads `/state` only after that load's first Playing, and ends on any stall, pause, interruption or backgrounding, since JS timers can stop while the 8x would not. `loadAndPlay` resets the rate to 1x because RNTP carries it to the next item. What it shed reaches the feed as `leadTrimMs`, so the track clock and the DJ's lines move with the listener.
- **Playback lines go through `plog` (`src/hooks/usePlayer.ts`), and are redacted before they are stored** (#2140). Release builds keep the last few hundred for the About sheet's Share playback log, so `src/lib/playback-log.ts` strips the station password, the Station login, URL queries and route device names first; a line that can carry a new kind of secret needs a rule and a test there. `PlaybackLog.add` never throws, because `plog` runs mid-reload and ahead of each event's dispatch: a line it can't redact is lost, never stored raw (#2160).
- **Every request to a station sends the Station login as a header, from `loginHeaders` (`src/lib/api.ts`)** (#764, #1873): API calls go to the credential-free base, and images get the header too. Android's fetch and image loaders, and AVPlayer, ignore URL userinfo.
- **A station's body read ends at its own deadline, and an abort alone doesn't end it** (#2163): `readJson` (`src/lib/api.ts`) gives every JSON read `FETCH_TIMEOUT_MS` for the headers, then the same again for the body, and stops at the caller's signal, so a new read goes through it, never a bare `res.json()`. It aborts the request and races the read, because native `text()` never settles after a cancel on iOS and resolves truncated on Android (its doc explains). The directory reads through it too, with one `FETCH_TIMEOUT_MS` across headers and body (`src/lib/directory-read.ts`). A test of it never awaits a read that can stall: a promise that never settles hangs `npm test` instead of failing it.
- **A Station login is checked with the station before it is saved, and only a 401 whose `WWW-Authenticate` asks for Basic counts as a proxy refusing it** (#1873). Two checks can read a login (`checkStationLogin`, `src/lib/station-login.ts`): a proxy guarding `/api` refuses a wrong one on `/api/health`, and with no proxy only the stream password reads it, through the same check `POST /station-auth` runs. After a proxy's refusal there is no "Save anyway"; after a stream-password refusal or an unchecked login there is (`saveAnywayOffered`), since a proxy that guards only the stream may still want it. A 403, a timeout or a network error never refuses one or stops the player, and nothing probes the stream, which would count a phantom listener. `/station-auth` reads a challenge of any scheme, like any 401 that is not the controller's own, as unverified on purpose (`stationAuthResult`), so a proxy never makes the app forget a station password; never unify the two rules.
- **Remote controls have no skip**, because every listener shares one live stream: `src/audio/player.ts`'s capability lists leave it out, and `service.ts` registers no handler.
- **No donate or tip link anywhere in the app.** Store payment policy forbids it (App Store 3.1.1, Play Payments); `src/lib/links.ts` explains.
